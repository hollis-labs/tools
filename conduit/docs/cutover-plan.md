## 1. What changes for the owner

Read this section first. Everything else is how it is done.

**Four things you could do before are gone, on purpose.** Approval is now a signed-in person's act and nothing else's.

1. **The terminal prompt.** `conduit approve <run>` no longer opens `/dev/tty`, shows the command and asks. A process that can
   run the binary and open the data file is not a person, and agents run on the same host.
2. **`-yes`.** `conduit run -yes` no longer approves its own run.
3. **`-shadow`.** The mode that recorded the verdict but did not require approval, so an Ask ran without one (Deny still blocked), is removed.
4. **Local `reject` and `token`.** `conduit reject` as a local command and `conduit token create|list|revoke` are removed.
   Keys are the identity module's: `conduit identity key create --name N --scope S --out FILE`.

What replaces them: `conduit approve --server URL --user NAME <run>` and `conduit reject ...`. You sign in as yourself, the
password is typed at the terminal (refused when stdin is not a terminal; there is no flag, environment variable or file for
it), the session lives in memory for that one request and is signed out again. Nothing is stored. Before anything is sent it shows the **whole** command (control characters made visible, never cut), the working directory, the effect and who submitted it, and asks you to type `yes`; anything else sends nothing. Reject asks for nothing.

**You set up your own sign-in.** You run `conduit identity setup` yourself at a terminal (step 6.5). Nobody generates your password and it is never written to a file, unlike the other apps: here a person's sign-in is the approval gate, and agents run as the same user as you. A token minted from your session is not a person either: it is a stored file, so it cannot approve. A page for approvals is a
later task.

**Also different:**
- The API moves from `/v1/...` to `/api/...` (conversion notes, "Routes"). `/v1/` answers a JSON 404.
- Scopes are renamed: `exec.read.own` is `conduit.read`, `exec.read` is `conduit.read.all`, `exec.run` is `conduit.run`,
  `exec.approve` is `conduit.approve`, `exec.admin` is `conduit.admin`. A key is no longer bound to a host.
- Every old token is **retired, not carried over**: its row is kept as history, and its hash as a bearer answers 401. Clients
  get new keys (section 12).
- Runs that were `pending` or `running` when the old service stopped are history, shown as such, and never started,
  approved or cancelled. Resubmit what is still wanted.
- The listener is `127.0.0.1:7421` only. Flags and variables (`-addr`, `-allow-dir`, `CONDUIT_BLOBS`, `CONDUIT_POLICY`) are
  keys in one file (section 6). OpenTelemetry is dropped (it was off).
- `/mcp` is served by `conduit serve` and needs a key with the scopes of the tools it calls.

## 3. Principles

- **The old files are never written.** `migrate-legacy` opens its source read-only and immutable, refuses an unmerged `-wal`
  and a target that is not empty. Rollback is: stop the new build, remove the drop-in, start the old build on the old files
  (section 11).
- **The new data directory is a new one: `~/.local/share/conduit-substrate`.** The default `~/.local/share/conduit` holds the
  old layout, which the new binary refuses; it is not used. The unit's drop-in sets `CONDUIT_DATA_DIR`.
- **No open setup window, ever.** `POST /api/setup` is refused (403). The owner and the first keys are created offline
  **before the service starts**; the first check after start is that `GET /api/setup` answers `{"setup_required":false}`.
- **The limit of approval.** A process running as the service's user can still write the database file directly. Approval protects against callers of the API and of the tools, not against that.
- **Never print a secret.** Keys are written to mode-600 files with `--out`, never to a terminal or a log; passwords are
  typed at a prompt.
- **The installer comes last.** `fleet-install deploy` restarts the unit, and the new `serve` refuses a data directory that
  holds only an old database, so the restart is only safe after the migration.

## 4. Step zero: before anything else, with nothing changed

Every run of the new binary that boots the modules (`serve`, `migrate-legacy`, `identity setup`, `identity key create`)
**creates** its data directory. Stray runs have no safe default:

1. List the data homes as the service's user, changing nothing: `find ~/.local/share/conduit ~/.local/share/conduit-substrate -ls`.
   Record the listing.
2. `~/.local/share/conduit` holds the old files (section 2). **`~/.local/share/conduit-substrate` must not exist.** If it does,
   stop and report: something has already booted the new build there.
3. Record `sha256sum` of `main.db` and every blob under `~/.local/share/conduit`, after the service is stopped, as the
   "before" for check 11.
4. Confirm `~/.config/conduit/conduit.yaml` does not exist yet (it is written in step 6).

## 5. Before the window (anyone, no downtime)

   `build-info.json` and `deploy.yaml`, built by `.github/workflows/conduit-build.yml`. Record the commit; it is the
   `--commit` of the deploy.
2. Keep the old binary aside, once: copy the installed artifact binary to a dated name next to it. It is the fallback for the
   first rollback (section 11).
3. Rehearse on a fresh online-backup copy, in a scratch directory with `HOME`, `XDG_*` and `CONDUIT_DATA_DIR` pointed there
   (section 10). Counts must match, the old copy's checksum unchanged.
4. Prepare, without applying: the config file (section 6, step 6), the Cerberus descriptor edit (section 8), the proxy edit
   (section 9). Tell whoever may be using the Conduit tools that they are unavailable for the window.
5. **A dry run of the installer**, by the driver, against the *published* artifact: `fleet-install deploy conduit --repo hollis-labs/tools --run <run id of the build on main> --dry-run` (the default workflow
   name `build.yml` does not exist in this repository, so `--commit` alone cannot find the run). It must print the checksum check, the link flip of `~/.local/bin/conduit`, the drop-in path, the unit
   restart and the `/healthz` poll on `7421`, and skip the preflight while the migrated database does not exist. The unit
   name in `deploy.yaml` is the one Cerberus generated for the resource; if the dry run reports another, fix `deploy.yaml` first.
   **Done on 2026-11-12** against the build of `main` at `e5a9267c64db` (run `43322242607`, artifact `conduit-e5a9267c64db`): checksum ok;

   `7421`, and skips the preflight because the migrated database does not exist yet. Nothing was changed on the host. `deploy.yaml`
   needed no change.
6. Read section 12 against what is found on the host: each caller gets a key, or is retired.

## 6. The window (host-run, in this order)

Every command runs as the service's user with its `HOME`. The new binary is extracted from the tarball into a scratch
directory first (`$NEWBIN`); it is **not installed yet**. The same environment is used for every host-run command, so each
one places the database, signing key and secrets exactly as the service will:

```sh
export SUBSTRATE_CONFIG=$HOME/.config/conduit/conduit.yaml
export CONDUIT_DATA_DIR=$HOME/.local/share/conduit-substrate
OLD=$HOME/.local/share/conduit
```

1. **Stop**: stop the unit through Cerberus (`service-stop`) or with `systemctl --user stop <unit>`; either is acceptable (the run
   used the second, because Cerberus refused a stop from a read-only session). Do not kill the process. Confirm no `conduit` process remains.
   Then step zero 3.
2. **Backup**, read-only on the old file: an online-backup copy of `$OLD/workspaces/default/main.db` to a new file in a
   backups directory (mode 0600). `sqlite3 <copy> 'pragma integrity_check'` must print `ok`.
3. **Config**: write `$SUBSTRATE_CONFIG` (mode 0600):
   ```yaml
   httphost:
     addr: "127.0.0.1:7421"
   conduit:
     allow_dirs: ["<the old allow-dir>"]
     policy_file: "<home>/.config/conduit/api-policy.yaml"
     blobs: "local"
   ```
   `identity.secure_cookies` stays `auto`: `conduit approve --server` signs in over loopback http, and a Secure cookie is not
   sent back there. Run `conduit config` and read the effective values before going on.
4. **`migrate-legacy`**: `$NEWBIN migrate-legacy --from <the backup copy> --blobs-from $OLD/blobs`. Expect `runs 2`,
   `attempts 2`, `panics 0`, `retired_tokens 1`, `blobs copied 1` (the counts of the day; the figure at the cutover is
   whatever the backup holds), `0 mismatches` and exit 0. It creates the data directory. A second run is refused.
5. **Identity, offline**: the owner runs `$NEWBIN identity setup --username <owner>` **himself, at a terminal** (the password is typed twice, not echoed; nobody else generates it and it is never written to a file or passed on), then for each
   caller of section 12 `$NEWBIN identity key create --name <caller> --scope <scopes> --out <new file in the caller's
   config directory>`. The key is in the file and nowhere else.
6. **Install**, last: `fleet-install deploy conduit --repo hollis-labs/tools --run <run id>` (the run of step 5). Its preflight backs up the migrated `conduit.db`; it
   writes the drop-in, flips `~/.local/bin/conduit` and restarts the unit; health is `GET /healthz` on `7421`.

## 7. Checks right after start

1. `GET /healthz` is 200.
2. `GET /api/setup` answers `{"setup_required":false}` and `POST /api/setup` answers 403. If setup is required, stop the unit now.
3. No credential: 401. A request for an unknown `Host`: 403. A retired old token as a bearer: 401.
4. `GET /v1/runs`: JSON 404.
5. Owner sign-in works; `GET /api/runs` lists the two migrated runs, both marked legacy; their output recalls.
6. Each new key answers its own calls (`POST /api/check`, `GET /api/runs`) and is refused where its scopes stop.
7. A key with `conduit.run` submits a command the policy asks about: the answer is `pending`. A key with `conduit.approve`
   asked to approve it answers 403. `conduit approve --server http://127.0.0.1:7421 --user <owner> <run>` approves it and it
   runs once.
8. A SIGTERM to the unit (a stop through Cerberus) exits within the drain.
9. The journal has no panic. A request for any `Host` other than a loopback name is 403 (the removed proxy name included).

## 9. The proxy

One name forwarded to `127.0.0.1:7421` with no `Host` rewrite. **Decided by the owner (2026-11-12): the name is removed.** No caller
was found, so nothing is served behind it afterwards, and the config has no `conduit.allowed_hosts` entry: Conduit answers only
loopback names, and a request for any other `Host` is refused with 403. The proxy edit (deleting the name's block and reloading the
proxy) is the owner's, done after the service is healthy.

If a name is wanted again later, the two ways are: the proxy rewrites `Host` to the loopback address (the MCP library's localhost
protection refuses `/mcp` otherwise; framework request open, Gap 4 in the conversion notes), or the name is listed in
`conduit.allowed_hosts` and the proxy sends exactly one `X-Forwarded-Proto: https` from a loopback peer (every other forwarding
header is dropped). Neither is in this cutover.

## 11. Rollback

Before the first deploy there is nothing to roll back: the old service is stopped and its files are untouched. If the new
build misbehaves after it:

1. Stop the unit. Remove `20-fleet-exec.conf` (or the installer's own rollback), `systemctl --user daemon-reload`.
2. Restore the old command in the Cerberus descriptor, or swap the dated copy of the old binary back to its path (section 5
   step 2). The old data (`main.db`, `blobs/`) were never written and are the rollback.
3. Start the unit; the old build serves the old files. What the new build recorded in `conduit-substrate` since the cutover is
   not in the old database. The old tokens work again in the old build.
